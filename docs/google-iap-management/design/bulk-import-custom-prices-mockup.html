Design mockup · hold for review

Google Bulk Import — pricing-source relabel + per-item Custom prices

Google IAP Management only. Part 1 renames Google default → Google Conversion and reorders the three cards — label only, the stored value stays google_default (DB CHECK constraint + every historical actions_log payload). Part 2 lets one item in the Step-3 preview override its prices per country, independently of the batch template.

Manager-locked

  • · all ~170 Google countries, searchable
  • · Custom survives a template change
  • · template sources only, not Google Conversion

Non-negotiable

  • · Custom is never opaque — always re-openable
  • · always revertible to the template
  • · a custom row that can't apply FAILS VISIBLY

Reuse, not a second editor

  • · shared RegionPriceCell with the detail view
  • · shared currency-precision.ts validation
  • · currency derived from country, display-only

STATE 6

Edge states — inactive Custom, file swap, and the failure path

Source switched to Google Conversion

Custom · 168 countries inactive — not applied under Google Conversion

Kept, not cleared: switching a radio must not destroy work the Manager cannot get back. Switching to a template source reactivates it unchanged. Not sent in the execute payload while inactive. (Recommendation — design doc §2.H Q4.)

Row set to Skip

Same treatment — chip greys out, nothing is sent (skip rows never reach Google).

A different file is uploaded at Step 2

3 custom price sets kept · 2 dropped

Kept where the SKU still appears in the new file (gem_pack_large, pack_starter_099, bundle_seasonal); dropped where it does not (gem_pack_small, vip_month).

Both counts are named — a silent drop-all loses real work, a silent keep-all is invisible. (Recommendation — design doc §2.H Q3.)

Page refresh

All wizard state is client-side, so a refresh loses customs — same as the preview rows themselves. A beforeunload prompt fires while unsaved customs exist, reusing the listener already registered for hub-tracking (BulkImportWizard.tsx:199-214).

· Row 6 (vip_month): custom prices carry no VND entry, which Google requires for defaultPrice. Row not sent.

The hard rule. A custom row that cannot be applied is excluded from the batch and named here. It never falls back to the template price — that would ship a price the Manager did not choose and report success for it. Reuses the existing per-row fail-soft channel (bulk-import.ts:459-467, BulkImportWizard.tsx:992-1011). Open question §2.H Q5: custom refusals should also count toward the Hub run’s terminal status, which today treats every refusal as a soft skip (hub-tracking/status-mapping.ts:33-45).

Execute contract — what actually changes

Per-row payload (additive)

rows: [{
  rowNumber, sku, baseCurrency, basePriceDecimal,
  regionOverrides, listings, decision,
  chosenTierIdentifier, defaultTierIdentifier,
  tierCandidateCount, priceHeaderSource,
+ customPrices: {
+   entries: [{ region, currency, priceDecimal }],
+   baselineTier: "tier_999" | null
+ } | null            // null unless source is a template
}]

Orchestrator — the one line that matters

// bulk-import.ts:555 — template loop skip guard
- if (row.crossCurrencyRefusal || row.resolvedDefaultPrice) continue;
+ if (row.crossCurrencyRefusal || row.resolvedDefaultPrice
+     || row.customPrices) continue;

Without it, bulk-import.ts:672-676 overwrites row.regionOverrides with the template entries and the custom prices vanish — silently, into a live store. Acceptance must break this guard and watch the test fail (P10 mutation-check), not merely watch a green test pass.

No migration

BULK_IMPORT_BATCH is already in the actions_log CHECK constraint; payload is JSONB. P2 verified.

Provenance per item

per_row_diagnostic[] gains price_provenance, custom_entry_count, custom_baseline_tier, custom_blank_regions.

defaultPrice

Taken from the custom entry matching the app’s default currency, stamped into the existing resolvedDefaultPrice field — so buildProduct needs no change.
