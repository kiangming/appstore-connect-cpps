Design mockup · hold for review

Apple IAP — per-territory Custom Prices

Apple IAP Management only (iap_mgmt). Override the price for ANY territory — including territories a pricing template already covers — by picking from the price points Apple actually supports there. Applies to the Edit form and the Create form. On submit the existing mechanism runs unchanged, with custom values winning per territory.

Manager-locked

  • · Create form AND Edit form
  • · custom beats template, per territory
  • · base change → STALE, never reset

Non-negotiable

  • · custom is never opaque — values always visible
  • · always revertible: one row, and all
  • · submit BLOCKED while stale (structural)

Apple-specific

  • · price points are OPAQUE IDs → always a select
  • · ~175 territories, auto-equalised from a base
  • · schedule POST is REPLACE-ALL, no PATCH

⚠ The clobber gate (G1) — the merge point is the whole feature

additionalPricePointIds is a flat, territory-anonymous array (pricing-orchestration.ts:260). Appending customs to it would send Apple two manualPrices for one territory. The resolution must be a Map<territory, …> where the custom loop's set() runs after the template loop's — that unconditional set is where custom wins, and it is the one behaviour the implementation must prove by breaking it.

Why read-only, not "editing it edits the base":

1 · The write path has one base slot (applePricePointId) and the template loop already excludes the base territory. There is nowhere for a second base to go.

2 · The base must stay a tier, not a price — tier_id is what the DB stores, what getTierUsdPrice resolves, and what the submit checklist validates. A free-picked USA point has no tier, so it would need a price→tier reverse lookup that can legitimately fail (~600 Apple points vs ~96 uploaded tiers).

3 · It would loop: editing the base re-fingerprints, marking every other row in the open dialog stale. The dialog would invalidate its own contents mid-session.

§C — three exits, no trap state

1 · One territory

The row's Revert ×, or picking the — use template … — placeholder. Both delete the map key.

2 · All territories

Footer and the form summary — so the Manager can escape without opening the dialog.

Clear 6 custom prices?

Those territories revert to template/auto. The values are written to the audit log (CUSTOM_PRICES_CLEARED) — that is the only recovery path.

3 · The whole session

Cancel discards the draft map. Presentation state is a separate object from custom_prices, which is only written on Save.

The empty array has exactly one meaning. custom_prices: [] = the Manager cleared them. undefined = the payload didn't carry the field, so the DB is left untouched. Never .default([]) in the zod schemas — that turns a threading miss into silent data loss.

Save as Draft stays ENABLED. A Manager mid-review must be able to persist without resolving. Only the two Apple-write buttons are blocked.

Why a comparison, not a boolean

Change Tier 15 → back to Tier 10 and the banner disappears on its own. Nothing to click, nothing logged. A one-way boolean would force the Manager to acknowledge a no-op.

"Keep them (reviewed)" re-stamps the fingerprint to the current baseline and changes no value. Change the base again → stale fires again. There is no reviewed: true flag anywhere — that is exactly the boolean this design rules out, and it would let a later baseline change go unnoticed.

Blocked is STRUCTURAL, on both layers, from one function

Client — Create/Update on Apple disabled + a red checklist item. Server — both write routes recompute the fingerprint and return 422 naming the two resolutions, before any Apple call.

One exported pure isCustomBaselineStale(form, storedBaseline) used by both. A client-only block is bypassable by a stale tab; a server-only block is a dead end with no way forward from the UI. A banner can be scrolled past — a disabled button cannot.

I.3 · re-validate on dialog OPEN. For templates the pick→submit window is one orchestration; for customs it is days. So every open refetches the list for territories that already have a custom (bounded by the customised count, typically < 10) and flags anything Apple no longer offers.

Submit path — one replace-all POST, custom wins at one guard point

The merge (pricing-orchestration.ts)

applyPricingSchedule(args + customPrices)
  ├─ skipped-no-tier / no-usd-price guards        unchanged
  ├─ base ← findPricePointByUsdPrice(basePts, usd)  unchanged
  ├─ overridesByTerritory = new Map()
  │   ├─ if source !== APPLE → template loop
  │   │     set(territory, {id, "template"})
  │   └─ ALWAYS: for each custom, territory !== base
  │        points ← same per-territory fetch
  │        match  ← findPricePointByUsdPrice(pts, price)
  │        match ? set(territory, {id, "custom"})  ◀ GUARD
  │              : missing.push({source:"custom", …})
  └─ setPriceSchedule({ applePricePointId,
       additionalPricePointIds: [...map.values()] })
Two gates would otherwise silently drop a customs-only edit — isEmptyDiff (5 clauses, no customs → route returns NO_CHANGES and the modal never opens) and runPricingStage.shouldRun (tier_changed || source !== APPLE → Stage 4 skipped). Both need a custom_prices_changed clause.
Customs apply under ALL THREE sources, including APPLE — so the custom loop sits outside if (source.kind !== "APPLE"). Google's equivalent shipped template-only and had to be re-scoped a cycle later; designed in from day one here.

Create-flow ordering + audit

  1. 1 New form → Save as Draft → customs persisted
  2. 2 redirect → Edit page → customs re-hydrated from DB
  3. 3 POST /v2/inAppPurchases → shell
  4. 4 localizations · getTierUsdPrice · poll ready
  5. 5 applyPricingSchedule — base + template + customs in ONE POST
  6. 6 screenshot · availability · GET state · mirror
Persistence is mandatory, not a nice-to-have. There is no "Create on Apple" on the New form (canCreate = mode === "edit" && !syncedToApple) — every create runs from the Edit page after a Save-Draft round trip. Client-only custom state would vanish silently.

Audit

  • · SET_PRICE_SCHEDULE payload gains custom_territory_count, custom_overrode_template_count, resolution_by_territory {custom, template, auto_fallback}, custom_territories[].resolved — no new action type needed.
  • · NEW CUSTOM_PRICES_REBASELINE — "Keep them (reviewed)" changes what ships while changing no visible value; without a row a later reader sees prices from one tier attached to another.
  • · NEW CUSTOM_PRICES_CLEARED — logging the values is the only recovery path.
⚠ KB P2 · the CHECK constraint. New action_type values are silently swallowed when absent from actions_log_action_type_check. Tracing this feature also found a live existing gap: the latest iap_mgmt CHECK (20260518000000) does not contain AVAILABILITY_SET_ALL_TERRITORIES or AVAILABILITY_REMOVE_FROM_SALES, both emitted today — those audit rows are being rejected right now. Same migration should close it.

Acceptance bar — prove it by breaking it (KB P10)

The one behaviour a mutation-check must prove

Given a custom and a template entry for the same territory, exactly ONE price point for that territory reaches setPriceSchedule — and it is the custom's.

  1. 1 Fixture: source APP_TEMPLATE with a VNM entry at ₫24,000 + a custom VNM at ₫25,000. Assert additionalPricePointIds holds exactly one ID whose decoded {t} is VNM — decodePricePointId makes this directly assertable — and that its {p} is ₫25,000's tier.
  2. 2 Break it: revert the Map to two independent additionalPricePointIds.push(...) calls.
  3. 3 Confirm the test FAILS with two VNM entries — not with an unrelated error. A test that still passes with the Map removed is a fake test: the fixture had no overlapping territory.
  4. 4 Revert, confirm green.

Secondary, same treatment, each guarding a G1 gate: delete the custom_prices_changed clause from isEmptyDiff → the customs-only Update test must fail with NO_CHANGES; delete it from shouldRun → the customs-only-under-APPLE test must fail with zero applyPricingSchedule calls.
